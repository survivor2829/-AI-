# 鱼水和 AI 物业助手：产品流程与 Demo 实现边界

## 结论

该概念可以实现为原生微信小程序 Demo，没有结构性技术障碍。核心原则是：

> AI 负责理解用户意图和组织表达；业务层负责房屋、账单、金额、订单状态与执行结果。

因此，模型不能自行生成账单金额，也不能直接发起支付。

## 首页交互形态

第三张方案中的服务面板不是下拉框，也不是侧边栏，而是底部服务抽屉（Bottom Sheet）。它有三种状态：

1. 首次进入：半展开，用于让用户立即看到 AI 能办理哪些事项。
2. 开始对话：自动收起，仅保留“全部服务”入口，让聊天成为主区域。
3. 用户点击“全部服务”或上拉：全展开，作为传统办理模式。

抽屉隐藏后，主页面会接近纯聊天界面；区别在于 AI 返回的是账单、进度、确认等结构化业务卡片，而不只是普通文字。

### 抽屉触发与收起规则

自动触发只发生一次：用户首次进入 AI 办事台，或主动新建一个空白会话时，抽屉默认半展开，用来说明 AI 的能力范围。

用户点击“全部服务”或向上拖动把手时，抽屉全展开。AI 无法识别意图时只提供“查看全部服务”按钮，不强制自动弹开抽屉。

发生以下任一行为时，抽屉自动收起为底部小入口：

- 用户点击快捷意图或发送第一条消息
- 输入框获得焦点、系统键盘弹起
- 用户选择某项传统服务并进入办理流程
- 用户向下拖动抽屉，或点击全展开状态外的背景区域

同一段对话中，用户手动收起后不再自动弹开；页面始终保留“全部服务”入口。用户点击对话页左上角“首页”时结束当前会话，返回能力发现页并恢复半展开服务抽屉。

## 四个关键页面状态

| 状态 | 页面重点 | 进入方式 |
| --- | --- | --- |
| 能力发现 | AI 输入框、快捷意图、半展开服务抽屉 | 首次进入 |
| 进入对话 | 聊天流、固定输入框、收起的服务入口 | 输入文字或点击快捷意图 |
| 账单与确认 | 结构化账单卡、查看明细、明确确认 | AI 完成查账 |
| 全部服务 | 缴费、交房、装修、搬家等传统入口 | 点击“全部服务”或上拉抽屉 |

## Demo 主流程

用户输入“帮我查一下物业欠费” → AI 识别意图 → 确定性业务层返回账单 → 页面展示账单卡 → 用户点击“确认缴费” → 再次确认 → 模拟支付 → 成功结果与电子回执。

语音在本轮只演示录音、识别中和播放状态，不接真实 ASR/TTS。

## 最小技术架构

```text
原生微信小程序
├─ AI 办事台页面
├─ Chat / BillCard / ServiceSheet / Composer / ConfirmCard
├─ 页面状态机：发现 → 对话 → 账单 → 确认 → 结果
├─ mockBusinessService：房屋、账单、订单真值
└─ aiClient
       ↓
云函数 aiGateway
├─ OpenAI-compatible 模型调用
├─ 固定 JSON Schema
├─ 意图白名单与字段校验
└─ 超时、错误及演示兜底
```

模型配置通过云函数环境变量提供：`MODEL_BASE_URL`、`MODEL_API_KEY`、`MODEL_NAME`。密钥不进入小程序代码。

## 本轮 Demo 不做

- 真实微信支付、支付回调、退款、对账和发票
- 真实业主身份与房屋绑定
- 真实物业系统接口的数据一致性
- 完整员工端、权限审计与工单后台
- 真实语音识别与语音合成

正式一期可保留前端交互，只需逐步把 Mock 业务层和模拟支付适配器替换为真实接口。

## 设计源码与生成产物

高保真页面源码位于 `design/`，OpenPencil 构建与导出脚本位于 `scripts/`。运行 `npm run design:build` 后，生成的 `.fig`、PNG 和独立页面截图会写入本地 `artifacts/` 目录。

`artifacts/` 属于本地设计交付和生成产物，不作为代码仓库内容；需要对外共享概念图或 Figma 文件时，应单独确认发布范围。
